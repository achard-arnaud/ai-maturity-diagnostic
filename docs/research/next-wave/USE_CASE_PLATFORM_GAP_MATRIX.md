## 0. The one thing every row shares

Every `/api/v1/workspaces/{workspace_id}/...` list route in this repo
follows one uniform shape: **single-field equality filters + cursor
pagination bounded to 1-100, no free-text search, no multi-field sort**.
`app/signal_routes.py`, `app/research_routes.py`, `app/demand_routes.py`,
`app/fit_routes.py`, `app/target_plan_routes.py`, `app/reach_routes.py`,
`app/engagement_routes.py`, `app/opportunity_routes.py` and
`app/network_v1_routes.py` all reject `limit` outside `[1,100]` and page
with an opaque `cursor`/`next_cursor` string keyed on the object's own id
field, sorted ascending by id. None of them accept a `sort` parameter or
a text query. This is noted once here rather than repeated nine times in
the table's "search" column, which instead only calls out each row's
*filter fields* (its deviation from this shared baseline).

## 2. Cross-cutting pattern (read once, applies to five of nine spaces)

Research, Targets, Reach, Engagement and Pipeline are **all** read-only
over HTTP, and in four of the five cases (Targets/Reach/Engagement/
Pipeline) the corresponding `EPIC_0X_ACCEPTANCE.md` says so in almost
identical language ("does not yet expose a write path... Python-API-only...
deferred, narrow follow-on work, same pattern as..."). This is not five
independent gaps discovered by this research pass — it is one repeated,
explicitly self-reported architectural choice (ship the read model first,
per-Epic, defer the write route) that a next-wave Epic could address
uniformly rather than five times over. See CRUD_SEARCH_ARTIFACT_GAP.md for
the object-by-object detail and a consolidated recommendation.

Only **Demand** (Epic 05) and **Fit** (Epic 07) got a full HTTP
create+patch path with optimistic concurrency (`expected_version` in the
PATCH body, 409 on conflict) — these two are the reference implementation
any future write-route work should copy, not reinvent.

## 3. UI pattern (generic cards vs. purpose-built)

Per ADR-010, E12 deliberately kept a small vanilla-JS shell and accepted
generic card rendering as in-scope, not a bug. Reading `gtm-spaces.js`
confirms that **seven of nine spaces** (Home, Discover, Research, Fit,
Targets, Reach, Engagement) render through the exact same generic
`itemsFrom()` → card-grid path, including Fit (which has the richest
backend of any space) and Pipeline (whose `board: true` flag only changes
how stage data is flattened into the list, not the rendering — it does
not produce an actual kanban board despite the naming). Only **Insights**
has bespoke rendering (`renderInsights()`). This matches ADR-010's own
framing exactly: generic cards were an accepted E12 scope choice, revisit
"only if the measured E12 component surface demonstrates a concrete
maintainability or performance limit," which this research pass makes no
claim about either way.
